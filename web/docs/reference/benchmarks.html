Benchmarks and tuning

How to measure​

# a full run: 20 000 hashes, including the dataset build
./zmrig/out/zmrig --bench=20000

# a quick check after a configuration change
./zmrig/out/zmrig --bench=15000

# the numbers for a dashboard (10 s warm-up + 15 s window)
./zmrig/out/zmrig --report --power 45

--bench uses the fixed seed 00112233…, a 76-byte blob and the lowest target, so every run hashes identical data and results are comparable. The dataset build (15–25 s) is outside the measured window.

Rules that make a number mean something:

  • Stop the miner before benchmarking. A running miner holds the huge pages; the bench then builds its dataset in ordinary memory and reports a figure that is too low. oneclick.sh bench stops and restarts the service to avoid this.
  • Measure on the machine in question. Absolute hashrate depends on the host; do not compare to the table below.
  • Run each configuration twice. Under 2 % is noise.

The same machine and binary in a quieter session: 1008–1103 H/s. That spread is the reason comparisons have to be relative.

C++ engine on the same machine, same session: 1075.7 H/s — the gap to the Zig engine is within run-to-run variance, not a performance claim.

The three settings that matter​

1. Huge pages​

The largest and least ambiguous effect. RandomX reads a 2 GiB dataset in a random pattern, and 4 KiB pages mean constant TLB misses.

# reserve 1234 pages of 2 MiB (≈2.4 GiB)
echo 1234 | sudo tee /proc/sys/vm/nr_hugepages
grep HugePages_ /proc/meminfo

The installer does this and writes it into the systemd unit (LimitMEMLOCK=infinity). To check the miner got them: startup logs huge pages 2336 MB, and the API reports "hugepages": [1168, 1168] (granted / needed).

A practical warning: with 1234 pages reserved, ordinary RAM is down to about 1.2 GB. Running --no-huge-pages at that point gets OOM-killed (exit 137), because the 2 GiB dataset has nowhere to live. Lower nr_hugepages to 0 first.

2. Fast or light mode​

fast builds one 2 GiB dataset shared by all threads → 814 H/s on this 2 vCPU machine. light keeps only the 256 MiB cache and recomputes the dataset per hash → 76 H/s.

Nearly 11×. light is defensible when the VPS does not have the RAM, or to test a configuration quickly (0.6 s startup instead of 20 s).

3. Thread count​

Linear on this machine: 2 threads = 814 H/s, 1 thread = 408 H/s. There is no hidden sweet spot. On a throttled shared vCPU, extra threads can lower per-thread hashrate while still raising the total; measuring is the only way to know.

Settings that made no measurable difference​

  • --scratchpad-prefetch 0/1/2/3: under 1.5 %, i.e. noise. Leave the default.
  • --no-affinity on 2 vCPU: nothing.
  • --no-optimized-init: affects dataset build time, not hashrate.

Ignore advice to raise priority for hashrate: priority changes how the OS shares CPU, it does not make arithmetic faster. It helps when the machine does other work.

The ten-minute tuning procedure​

# 1. background state
sudo ./oneclick.sh stop
grep -E "HugePages_Total|HugePages_Free" /proc/meminfo

# 2. measure the default
./zmrig/out/zmrig --bench=15000

# 3. variants, each twice
./zmrig/out/zmrig --bench=15000 -t 1
./zmrig/out/zmrig --bench=15000 --no-huge-pages   # only after lowering nr_hugepages
./zmrig/out/zmrig --bench=15000 --mode light

# 4. keep the winner in the config, then start
sudo ./oneclick.sh start

Write the numbers down with the date and host name. Six months later you will want them.

Heat and power​

Hashrate is not the whole story. A machine doing 814 H/s at 95 W beats one doing 900 H/s at 130 W. Measure at the wall, or read package power from RAPL:

cat /sys/class/powercap/intel-rapl:0/energy_uj   # twice, one second apart

zmrig --report reads it for you and records the source in the report code (pwsrc: rapl, hwmon, user or none), along with hw — hashes per watt (the 60-second hashrate divided by power). That is the number --profile watt optimises, so the code carries it instead of leaving everyone to divide.

hashratepowerH/W
--profile freethe most the machine can dohighestlower
--profile watta few percent lower (SMT threads dropped)30–40 % lower on the SMT parthigher

Those rows describe a direction, not your machine: power cannot be measured inside this repository's container (RAPL is blocked), so the watt figures are inferred from P ∝ V²·f and published SMT data. The hashrate side is measured. On a machine with RAPL, run zmrig --report under both profiles and compare hw — then the conclusion is yours, at your electricity price.
